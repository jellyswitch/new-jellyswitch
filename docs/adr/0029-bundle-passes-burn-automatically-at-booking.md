# Bundle passes burn automatically at booking

A member holding a day-pass bundle who books an included room is declaring intent to spend a pass on that date — so the server burns one automatically, instead of demanding an explicit `use_bundle_pass` flag and 422ing when it's absent. Decided by David 2026-09-01 after the Pratik incident at Cowork Tahoe (2026-08-26): a brand-new member bought a 2-pack, tried three times to book included rooms for the next day from the **web calendar**, and every attempt dead-ended in `EnforceCoverage`'s *"This room needs a day pass for Aug 27. Use a pass or buy one to book it."* — with no affordance to actually use one. He bought a second $70 bundle thinking the first purchase had failed; an admin had to refund the duplicate, `schedule_bundle_days` the dates, and book on his behalf.

Root cause was a client-contract gap, not a billing bug: ADR 0019's coverage work (P8, 2026-07-01) added `enforce_coverage: true` to `Operator::ReservationsController#create` — the POST target of **both** the today-only Reserve Now page and the calendar booking sheet — but only Reserve Now was taught to fetch coverage and send the decision flags. The calendar sheet (the only web surface that books future dates) never sends them, so every included-room calendar booking since 7/1 was hard-blocked. The same 422 hits any API client that omits the flags (e.g. a mobile build predating the coverage-confirm sheet). `RedeemBundlePass` itself always handled future dates correctly.

**The rule now:** `RedeemBundlePass` runs in auto mode whenever the caller sets `enforce_coverage` (the member-self-serve marker) and the room is included — exactly the flows that would otherwise 422 now cover themselves. Every existing guard still applies: an existing pass for the date, a prior burn in the business-day window, subscribers/leaseholders, and paid rooms all skip the burn; a member with NO bundle still gets the 422 with the buy prompt, because **spending new money stays an explicit choice** (`buy_day_pass` is never auto-set — that's ADR 0019's deleted silent auto-buy staying deleted). The mobile confirm sheet ("This booking uses 1 of your N passes") keeps sending the explicit flag — same outcome, better-informed member. Doors already behave this way (`ConsumeOnEntry` burn-on-entry, ADR 0017) — booking now matches the door. Admin/on-behalf flows don't set `enforce_coverage` and keep explicit control (`schedule_bundle_days`); admins can also refund a burn (`refund_pass_locked!` / bundle +/- adjust) if a member changes plans.

Also fixed here: `EnforceCoverage` now evaluates coverage against the **room's** location (parity with the burn, which mints against `room.location`) — previously a member whose `current_location` differed could burn a pass and still fail the booking as "uncovered."

## Considered Options

- **Teach the web calendar JS to fetch coverage and prompt** — rejected as the primary fix: repairs one surface; old mobile builds and any future client with the same omission stay broken. Server-side auto-burn fixes the class. (A calendar-side "this used a pass" notice remains a nice-to-have.)
- **Auto-set `buy_day_pass` too when there's no bundle** — rejected: silently charging money is the exact dark pattern ADR 0019 removed. Blocked-with-buy-prompt is correct for non-holders.
- **Relax `EnforceCoverage` to allow uncovered bookings** — rejected: reopens the free-room/no-access hole the guard exists to close.
- **A new explicit `auto_redeem` context flag from each caller** — rejected: `enforce_coverage` already marks precisely "member self-serve coverage semantics apply"; a second flag can drift from the first.
